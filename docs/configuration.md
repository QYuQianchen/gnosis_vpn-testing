# What you have to provide

Everything in the kit has a working default except the items below. They are
sorted by when you hit them, and each says what happens if it is wrong — a
setting that silently produces a plausible-but-meaningless result is worse than
one that fails loudly, and two of these are in the first category.

## Only for the `pin-cfg-*` arm

| What | Where | Notes |
|---|---|---|
| Blokli URL | `BLOKLI_URL` | defaults to `https://blokli.jura.hoprnet.link`; the only endpoint needed |
| `blokli-inspector` on PATH | `--blokli-bin` to override | build from github.com/hoprnet/blokli-client |
| `eth-account` | `pip install eth-account` | signing only |

`tools/close-channels.py` reads the channel set, contract address, grace period,
gas price and nonce from blokli, signs with the node's own key, and broadcasts
through blokli. Plan-only by default; `--send` is the confirmation.

## Before anything runs

| What | Where | Notes |
|---|---|---|
| **SSH alias `gvpn-vm`** | `~/.ssh/config` on your Mac | Host, user, key/agent. `make push` and every `scp` in the docs use this name. |
| **Faucet codes** | `~/gvpn-state/secrets/faucet-codes` on the VM, one per line | Only for arms that re-onboard. **No shipped arm does** — `pin-cfg-*` used to and no longer does. Keep them for a hand-built arm that needs a fresh identity; `./tools/faucet-codes.sh` says how many are left. |
| **Backup passphrase** | typed at `make backup` | Not stored anywhere. Lose it and the backup is scrap. Put it in your password manager before you type it. |

Nothing else is a secret. The node identity is generated by onboarding, not
supplied by you, and the safe/module addresses are read off the node by
`make arms` rather than typed.

## `gvpn.conf` — defaults for this machine

Edit once. Everything here can be overridden per study or by a flag.

| Field | Default | Provide your own when |
|---|---|---|
| `GVPN_CHANNEL` | `stable` | you want `snapshot` (nightly) or `experimental`. Changing this can move the client across release lines, so the available networks change with it. |
| `GVPN_NETWORK` | `jura-prod` | testing against `jura-dev` or `piz-palu-dev`. Must match the channel. |
| `GVPN_PIN_VERSION` | *(empty = newest)* | **Set this before a study starts.** See below — this is one of the two that silently ruins results. |
| `GVPN_DESTINATION` | `UK` | your config.toml names exits differently, or you want a different single exit. `make arms` fails loudly if the name is not in `config.toml`, so a typo here is caught. |
| `GVPN_ALLOW_INSECURE` | `1` | only needed for the `zero-hop` arm. Harmless otherwise. |
| `GVPN_PING_TARGET` | `1.1.1.1` | your network blocks it, or you want the in-tunnel RTT measured against something else. |
| `GVPN_DL_URL` / `GVPN_UL_URL` | Cloudflare speedtest | you would rather not depend on a third party, or it is unreachable from the VM. **Verify both respond from the VM before a long run** — see below. |
| `GVPN_IPERF_SERVER`, `GVPN_UDP_HOST` | *(empty)* | you have a second VPS. Not required: `--target url` measures both directions, plus loss and jitter, from the one VM. |
| `GVPN_LOG_SIZE`, `GVPN_LOG_KEEP` | `200M`, `20` | your disk is small. Planner DEBUG logging produces roughly 100 MB/hour. |

## `studies/<date>-<name>.conf` — one per experiment

Copy the existing one and change the date. **Do not edit a study file after its
run has started** — an edited study is one whose arms were not all measured the
same way, and nothing in the output would say so.

| Field | Provide |
|---|---|
| `GVPN_PIN_VERSION` | the exact apt version, e.g. `2026.09.17+build.134506`. `./setup/05-set-version.sh --list` shows what is available. |
| `GVPN_ARMS` | which arms to compare. Default `auto pin-planner no-explore`. Adding a `pin-cfg-*` arm means faucet codes and a replaced identity. |
| `GVPN_DESTINATIONS` | one exit (cheapest, cleanest) or several (exit becomes a dimension, multiplies wall clock). `--dry-run` shows the cost. |
| `GVPN_REPS`, `GVPN_REP_GAP` | transfers per held-open session, and the gap between them. Default 5 × 300s. |
| `GVPN_FLOOR_MBPS` | the floor threshold. **Set it before the run, from the quick run's `auto` p25.** See below. |

## The two that silently ruin a result

Everything above fails visibly if you get it wrong. These two do not.

**`GVPN_PIN_VERSION`, left empty during a study.** Each arm installs whatever is
newest at the moment it runs. A mid-run upgrade splits the dataset in a way
interleaving cannot repair: you end up comparing versions rather than routing
modes, and the tables look completely normal. Pin it before the first cycle and
leave it pinned for the whole study. The manifest records what actually ran, so
you can check afterwards — but only afterwards.

**`GVPN_FLOOR_MBPS`, chosen after seeing the results.** "Sessions below the
floor" is the headline number of this whole exercise, and it means nothing
against a threshold picked once you know what the pinned arm did. Run `quick`
first, take `auto`'s p25, put it in the study file, and do not revisit it. The
bench records it in the manifest and `make report` reads it from there; passing
`--floor-mbps` later still works but the report prints a caveat saying it was
overridden and what the study had declared.

## Verify before a long run

```sh
# on the VM, tunnel up
curl -s -o /dev/null -w '%{http_code} %{size_download}\n' \
     "https://speed.cloudflare.com/__down?bytes=1000000"
head -c 1000000 /dev/zero | curl -s -o /dev/null -w '%{http_code}\n' \
     --data-binary @- "https://speed.cloudflare.com/__up"
```

Both must return `200`. I could not test these endpoints from where the kit was
built, so this check is yours — a 36-hour soak against a URL that 404s produces a
directory full of nothing.
